# Wayside 设计决策与开发方向

> 项目：Minecraft NeoForge Mod — Wayside  
> 整理日期：2026-10-18  
> 当前版本基线：v0.0.4  
> 文档状态：方向暂定，随实现和实测修订

本文记录项目为什么选择当前方向、哪些判断仍需验证，以及下一版本准备解决什么问题。依据是“反思Mod方向”讨论的可读取片段及本次整理补充；未进行源码审计，不补写缺失对话中的具体方案。

**设计方向、版本目标和已实现功能是三回事。本文中的愿景与计划不构成功能完成声明。**

## 1. 状态约定与当前基线

| 状态 | 含义 |
| --- | --- |
| 已确认实现 | 当前已知的版本能力；发布时仍应以代码和验证记录为准 |
| 暂定方向 | 当前按此推进，遇到实现证据可以调整 |
| 待验证假设 | 值得尝试，但尚不能视为成立 |
| 未决定 | 具体方案尚未选择 |
| 未来规划 | 保留在长期方向中，不自动进入近期版本范围 |
| 版本目标 | 准备交付的内容，验收前不算已实现 |

### v0.0.4 已确认实现

- 基本方块搜索。
- 基本寻路。
- 不可达缓存。

讨论中认可：寻找树木等目标时，当前阶段将不可达目标缓存后换一个目标，已经足以处理这类简单失败。

**尚未确认实现**：需求系统、完整采集与生存闭环、方块拆除、物品拾取或库存管理、建造、聚落、职业设施、社会与文明演化、土地宣称及保护。列在这里不代表判定代码中一定不存在，只表示本文没有足够依据将其写成现成功能。

## 2. 长期体验与演进方向

Wayside 希望从一个 NPC 能够自主应对基本生存需求开始，逐步发展出有生活感的聚落、职业与设施，再探索社会关系和文明演化。

体验参照是 Skyrim 式的奇幻世界：NPC 有自己的生活动机，世界具有可观察的活动与变化。这个参照用于判断世界体验，不等于承诺复制 Skyrim 的全部系统。

暂定的推进顺序是：

1. **单 NPC**：让简单需求能够触发行为，行为产生可验证的结果。
2. **聚落、职业与设施**：在单体行为可以工作后，逐步引入分工、设施使用和协作。
3. **社会与文明演化**：在前两者提供足够事实之后，探索更长期的组织与变化。

这是依赖关系和探索顺序，不是已经排定版本或日期的交付表。复杂世界是否能由简单规则逐步形成，仍然需要验证。

## 3. 已暂定的设计方向

### D-001：从单 NPC 的简单闭环开始

先解决一个 NPC 在具体场景中为什么行动、怎样完成行动、失败后怎样继续。每次增加复杂度，都应能说明它解决了哪个已经出现的问题。

为未来铺路主要靠清楚的行为边界、命名和适度通用化。近期不以完整的聚落、社会或文明框架作为单 NPC 行为的前提。

### D-002：以需求驱动行为

暂定采用“需求产生行动动机，行动结果反馈到需求或世界状态”的思路，而不是只把 NPC 写成固定巡回执行的脚本。

需求如何表示、如何比较优先级、多久评估一次，尚未决定。“需求驱动”是设计方向，不代表已经选定行为树、GOAP、效用 AI 或其他具体架构。

### D-003：复用基础行为，按实际重复提炼

目标搜索、移动，以及未来实现的世界交互，应尽量成为可以组合和复用的基础能力。同一能力以后可以服务于不同需求或职业，避免为每个职业复制整条行为链。

先把真实场景做通，再提炼已经出现的共性。概念上可以区分动机、目标、执行和结果，但不要求立即为每个概念建立独立框架或大量抽象类。

### D-004：失败处理先覆盖眼前场景

当前认可的简单策略是：目标不可达时使用已有缓存并更换目标。失败需要结合具体行为分析，不提前穷举所有未来异常。

新行为至少应说明成功条件和失败后的去向。后续若观察到反复重试、长期停滞或缓存失效问题，再按证据补充规则；不把当前策略写成已经解决所有动态世界问题。

### D-005：保留直接清障的原型取舍

对于确实需要清障的行为，讨论中接受了“玩家放置的普通方块也可以直接拆除”的简化方向。玩家放置这一事实，暂不单独成为禁止清障的理由。

这是一项行为设计取舍，**不代表 v0.0.4 已实现拆除或方块归属识别**。具体可破坏对象和触发条件仍需在实现该行为时明确，并与未来的保护规则衔接。

### D-006：性能通过实测判断

搜索、寻路、失败重试和未来的多 NPC 行为都应以实际场景观察为依据。先留下可复现的基线，再决定是否需要优化或改变设计。

目前不声明可支持的 NPC 数量、固定搜索成本或性能已经足够，也不提前承诺线程模型、全局调度器或复杂缓存体系。

### D-007：土地权限纳入未来规划

未来希望能够保护 NPC 建造的房屋，并允许玩家宣称自己的区域，约束 NPC 对世界的修改。

选区工具、按区块宣称都是候选方式；讨论中的木斧选区和 FTB 式区块仅是交互参照，尚未选择方案，也未确定相关依赖。

在新增世界修改行为时，尽量让允许或拒绝操作的判断容易接入；不为此提前实现完整的领地系统。保护对象、边界、冲突处理和存档方式仍属未决定事项。

## 4. 待验证假设

| 编号 | 假设 | 验证方式或触发时机 |
| --- | --- | --- |
| H-001 | 少量基础行为可以支持不同需求和未来职业 | 第二个真实行为场景出现时，检查是否能复用，而不是靠大量特殊分支勉强共用 |
| H-002 | 简单的需求驱动逻辑足以支撑早期自主行为 | 先观察单一需求的重复闭环，再在出现多个真实需求时验证选择与切换 |
| H-003 | 当前不可达缓存与换目标策略足够应付近期场景 | 测试可达与不可达目标混合、无合适目标，以及重复运行时的表现 |
| H-004 | 搜索和寻路成本可以在目标规模下接受 | 先记录单 NPC 基线；具备多 NPC 场景后逐步增加规模并测量 |
| H-005 | 个体行为与设施、分工可以逐步支撑更复杂的社会变化 | 后续按小场景验证；若必须加入显式规则，则记录原因，不预设文明一定自然涌现 |

这些假设的成立与否，应推动决策修订，而不是为了保留原设计而忽略反例。

## 5. 未决定事项

- **需求模型与调度**：先实现哪种需求、如何表示强度、如何选择与中断行动。
- **具体 AI 架构**：是否需要专门的决策算法或任务框架，现有结构在哪一步才需要拆分。
- **行为结果与重试**：成功、失败、等待如何表达；缓存何时失效；目标变化后何时再次尝试。
- **世界修改规则**：可以修改哪些方块、何时允许清障，以及未来权限怎样介入。
- **聚落、职业与设施**：成立条件、分工方式、设施识别与使用规则；不提前锁定完整社会模型。
- **土地权限**：选区还是区块、如何归属、如何处理重叠、NPC 房屋怎样受到保护。
- **性能目标**：目标硬件、NPC 规模和可接受开销；具体指标需要基线支持。

这些问题不要求一次全部回答。只有直接阻碍当前场景时，才需要先做最小决策。

## 6. 下一版本 v0.0.5 的目标

**本次整理确认的目标：完成单 NPC 的最小需求—行为闭环，并留下可复现的实测记录。**

下面的验收项用于落实这个目标，尚未执行或通过。具体选择哪种需求和行为，应在检查现有代码后写明；不能假定完整采集、库存等前置能力已经存在。

### 6.1 一个需求、一个明确场景

- 选定一种需求及其对应行为，写清触发条件、行为结果和停止条件。
- 形成“需求触发 → 选择目标或行为 → 执行 → 结果反馈”的最小循环。
- 结果必须实际改变需求或相关状态；仅搜索到方块或走到目标附近，不能自动视为生存闭环完成。
- 如前置能力不足，缩小场景或补齐最少能力，并记录本版实际支持的边界。

寻找树木可以沿用已有搜索与寻路作为候选场景，但是否涉及砍伐、拾取或库存，需要另行明确，不能由这个例子默认推导出来。

### 6.2 整理该场景实际需要的基础行为

明确搜索、移动、执行及结果反馈之间的责任，沿用可用能力；只有出现真实共性时才提炼。验收重点是行为能工作、结果能观察、边界能说明，不以建立通用框架为完成标准。

### 6.3 验证正常与失败路径

| 场景 | 期望结果 |
| --- | --- |
| 存在可达且合适的目标 | NPC 执行行为，产生明确结果，并反馈到需求或相关状态 |
| 部分目标不可达 | 使用现有不可达处理并尝试其他候选；不会持续卡在同一失败目标 |
| 没有合适目标，或候选均不可用 | 能结束本次尝试或进入明确等待，避免无间隔反复搜索 |
| 需求满足后再次触发 | 可以重新进入同一闭环，不只成功运行一次 |

等待多久、重试频率和缓存有效期由实现与观察决定，不在本文中虚构数值。

### 6.4 留下实测记录

记录游戏与 Mod 版本、运行环境、NPC 数量、场景布置、观察时长、复现步骤和结果。以单 NPC 为本版基线；多 NPC 扩展测试留到具备相应场景时。

使用现有工具或少量必要日志，记录能够可靠取得的性能数据及异常现象。如果只做了现象观察，应如实标注；不将其写成量化性能结论，也不要求为此先建设完整监控系统。

### 6.5 完成标准与范围边界

发布 v0.0.5 前，应能够展示同一场景的重复闭环、说明上述失败路径的实际表现，并提供实测记录。若有未达成项，记录缺口并调整版本范围，不把“计划完成”改写成“已经完成”。

聚落、职业设施、社会与文明演化、土地宣称，以及完整的通用 AI 框架，不是本版本的必交目标。

## 7. 仓库位置与维护方式

将本文件放在仓库根目录下的 `docs/DECISIONS.md`。它用于保存设计理由与当前方向；README 负责项目入口与使用说明，版本更新记录负责描述实际交付内容。

可在仓库根目录的 README 中加入：

```markdown
[设计决策与开发方向](docs/DECISIONS.md)
```

后续维护遵循以下规则即可，无需为每次小修改增加流程：

1. **方向变化时更新决策**：保留 D-001 等编号，记录日期、改变的原因和替代方向。被替代的决策留下简短说明，避免丢失上下文。
2. **获得证据时更新假设**：注明验证环境与结论；结果可以是成立、部分成立、被推翻或仍不确定。
3. **选定方案时关闭未决定事项**：将结果写入对应决策，不让已解决问题长期留在待定列表。
4. **发布时核对实现状态**：以代码与验收结果更新版本基线，把实际功能写入更新记录，并将下一版本目标换成新的目标。

可将具体测试记录和相关讨论通过仓库内文档或 Issue、PR 链接关联到对应条目。**编辑设计文档不会自动意味着代码已实现或版本已发布。**
